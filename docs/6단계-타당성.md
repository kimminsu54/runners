# 6단계 타당성 — 서버가 아니라 브라우저의 더 나은 모델

설계 문서의 6단계는 **서버 쪽 참조 파이프라인**입니다. 3단계 조사가 일곱 갈래를 다 막고
"더 나은 발 신호가 필요하다"로 끝났으므로 그것을 재 봤습니다.

**결론: 서버는 두 제약에 다 걸리고, 재 보니 브라우저에서 할 수 있습니다.**

## 서버 경로의 두 제약

### 실행 시간

이미 돌린 여섯 클립의 기록입니다. 전부 12초 창, `performance` 모드, 이 CPU.

```
01  463.5s  ( 39x 실시간)
02  544.5s  ( 45x)
03  544.8s  ( 45x)
04 5860.2s  (488x)   ← 이상치
05  534.8s  ( 45x)
06  635.1s  ( 53x)
```

**12초 클립에 8~10분**입니다. clip 04는 98분이 걸렸습니다.

`balanced` 모드로 clip 06을 같은 창에 다시 돌렸습니다 — **132.2초**(11x 실시간). 4.8배
빠르지만 여전히 12초 영상에 2분이고, 사용자를 기다리게 하는 종류의 시간입니다.

### 개인정보 약속

`src/app/page.tsx:91` 에 이렇게 적혀 있습니다.

> 영상은 업로드되지 않고 브라우저 안에서만 처리됩니다

서버 경로는 픽셀이 필요합니다(RTMPose가 이미지를 봅니다). 즉 **영상 업로드**이고, 이
문장과 정면으로 충돌합니다. 옵트인으로 문구를 바꿔 피할 수는 있지만, 그건 제품의 약속을
깎는 일입니다.

## 브라우저에서 될까 — 됩니다

### 모델은 표준 ONNX입니다

```
입력  [batch, 3, 256, 192] float
출력  simcc_x [batch, 26, 384] · simcc_y [batch, 26, 512]
크기  56 MB (rtmpose-m, HALPE-26, 256x192)
```

커스텀 연산자가 없습니다. SimCC 디코딩은 축마다 argmax 후 분할비(각각 2)로 나누는 것이라
JavaScript 열 줄입니다. `K = 26` — 발꿈치·엄지·소지 여섯 점이 들어 있는 그 세트입니다.

`rtmlib` 의 티어 매핑은 이렇습니다.

```
performance  yolox_x   (378MB) + rtmpose-x (191MB, 384x288)  ← 지금까지의 "기준"
balanced     yolox_m   ( 97MB) + rtmpose-m ( 56MB, 256x192)
lightweight  yolox_tiny        + rtmpose-s
```

### 사람 검출기는 필요 없습니다

RTMPose는 사람 박스를 받아 그 안에서 자세를 찾습니다. **MediaPipe가 이미 33개 랜드마크를
주므로 박스는 거기서 나옵니다.** 검출기(yolox_m 97MB)를 받을 필요가 없고, 자세 추정만
바꾸는 것이므로 지금 파이프라인의 나머지가 그대로 남습니다.

### 속도를 브라우저 엔진으로 직접 재봤습니다

`onnxruntime-web` 은 브라우저와 같은 WASM 빌드를 Node에서도 돌립니다. 그래서 추정이 아니라
측정입니다(같은 모델, 같은 엔진).

```
native  1스레드          41 ms/프레임   → 360프레임 15초
WASM    1스레드 SIMD    141 ms/프레임   → 360프레임 51초
WASM    4스레드 SIMD     67 ms/프레임   → 360프레임 24초
```

런타임 내려받기는 코어 WASM **14 MB** 입니다. 모델 56 MB 와 합쳐 **70 MB**, 한 번 받고
캐시됩니다(MediaPipe의 heavy 모델이 29 MB인 것과 비교할 수 있습니다).

### 품질이 문제를 실제로 고칩니다

이게 핵심입니다. 3단계에서 막힌 것은 clip 06에서 **MediaPipe가 한 접지를 둘로 쪼갠다**는
것이었습니다(구간 좌26/우23, 스트라이드 0.70s에 간격 0.368s). 같은 클립, 같은 12초 창을
두 티어로 돌린 결과입니다.

```
                              착지  접지    힘       구간      길이중앙
performance (rtmpose-x 191MB)  33   313ms  1.94BW  좌17/우17  0.267s
balanced    (rtmpose-m  56MB)  33   338ms  1.84BW  좌17/우17  0.317s
브라우저 (MediaPipe)            31   170ms  2.87BW  좌26/우23  0.134s
```

**작은 모델이 큰 모델과 똑같이 17/17 — 스트라이드마다 접지 하나 — 를 찾습니다.** 분절이
없습니다. 두 티어의 차이는 접지 8%, 힘 5%이고, 이건 브라우저의 +48% 오차와 비교할 수준이
아닙니다.

### 배관이 이미 있습니다

HALPE-26을 분석에 넣는 코드가 TRC 가져오기용으로 이미 쓰여 있습니다 —
`halpe26ToPoseFrames`, `MARKER_TO_MEDIAPIPE`, 소지 처리, 발 축 선택. 새 자세 소스는
그 앞단만 필요합니다.

## 그래서 제안

**서버를 세우지 말고 브라우저의 자세 모델을 올립니다.** MediaPipe는 사람 박스와 폴백으로
남기고, 정밀 분석은 RTMPose로 합니다. 영상은 여전히 나가지 않고, 3단계가 필요하다고
결론 낸 발 신호를 얻습니다.

## 아직 재지 않은 것

정직하게 적어 둡니다. 이걸 결정으로 쓰기 전에 확인해야 합니다.

**폰에서 재지 않았습니다.** 위 숫자는 데스크톱 CPU입니다. 중급 폰은 3~5배 느릴 수 있어
360프레임에 70~120초가 될 수 있습니다. 옵트인 "정밀 분석"으로는 그래도 쓸 만하지만,
기본 경로로 삼을 수는 없습니다. **이것이 가장 중요한 미측정 항목입니다.**

**WASM 스레드는 헤더가 필요합니다.** 4스레드는 `COOP`/`COEP` 를 켜야 하고, 그러면
교차 출처 자원 로딩 규칙이 바뀝니다. 1스레드로도 51초라 못 쓸 정도는 아닙니다.

**전처리는 이제 검증됐습니다** — 아래 절을 보세요.

**`rtmpose-s` 는 안 재봤습니다.** 더 작고 빠릅니다. 56MB가 부담이면 그쪽이 후보이지만,
접지를 17/17로 찾는지는 확인해야 합니다 — 이 문서의 근거는 `m` 에 대한 것입니다.

**70MB 내려받기.** 모바일 데이터에서 어떻게 다룰지는 제품 결정입니다.

## 이 조사에서 만든 것

측정용으로 `onnxruntime-web` 을 `--no-save` 로 설치해 재고 지웠습니다. `package.json` 과
잠금 파일은 건드리지 않았습니다.

`out/06-balanced/` 에 balanced 모드 실행 결과를 남겨 두었습니다(`out/` 은 gitignore).
기준으로 쓰던 performance 실행은 `out/06` 에 그대로 있습니다.

## 전처리를 구현해 대조했습니다

이 계획에서 코드가 없던 유일한 조각이 박스 → 모델 입력 어파인이었고, 그건 조금 틀리면
**모든 키포인트를 옮기면서 아무것도 실패시키지 않습니다.** 그래서 짜고 나서 눈으로 보는
대신, `rtmlib` 이 같은 프레임에 대해 만든 것과 숫자로 대조했습니다.

`rtmpose-reference.py` 가 한 프레임의 원본·입력 텐서·중심·스케일·키포인트를 내보내고,
`rtmpose-browser-check.mts` 가 전부 다시 만들어 비교합니다.

### 입력 텐서

```
center  336.23, 750.11   (참조와 동일)
scale   498.16, 664.21   (참조와 동일)
텐서 차이  평균 0.0023 · 최대 0.0088   (1.0 ≈ 58 그레이레벨)
```

평균 0.13 그레이레벨. 반올림 수준입니다.

### 전체 사슬

같은 프레임·같은 박스·같은 모델로 `rtmlib` 의 전체 통과와 비교했습니다.

```
왼발목    (360.88,  961.57) vs (360.88,  961.57)   0.000px
오른발목   (388.12, 1021.24) vs (388.12, 1021.24)   0.000px
왼엄지    (320.66, 1039.41) vs (320.66, 1039.41)   0.000px
오른엄지   (327.15, 1052.38) vs (327.15, 1052.38)   0.000px
왼발꿈치   (392.01,  966.76) vs (392.01,  968.06)   1.297px
오른발꿈치  (417.96, 1032.92) vs (417.96, 1032.92)   0.000px

26개 전체: 평균 0.050px · 최대 1.297px · 정확히 일치 25/26
```

유일한 차이가 **정확히 SimCC 한 칸**입니다(0.5 입력픽셀 × 664.21/256 = 1.297px). 니어타이
argmax에서 WASM과 native 런타임의 부동소수 차이로 옆 칸이 이긴 것이고, 로직 오류가
아닙니다.

### 걸려 넘어진 두 가지

기록해 둡니다. 둘 다 그럴듯하게 틀리는 종류입니다.

**반 픽셀.** 어파인은 박스 중심을 출력 픽셀 **(96, 128)** 에 정확히 맞춥니다 — OpenCV는
픽셀 중심을 정수 좌표에 둡니다. 그래서 표본점은 `중심 + (x − 96)·sx` 이고 반 픽셀
보정이 **없습니다.** 픽셀 면적 표본화의 관례대로 ±0.5를 넣었더니 0.31px 어긋났고, 그게
평균 6 그레이레벨로 나타났습니다.

**허용 오차를 모델보다 엄격하게.** 처음 판정 기준을 "1픽셀 이내"로 뒀는데, 모델 출력은
양자화돼 있어 한 칸이 1.297px입니다. **모델이 표현할 수 없는 정밀도를 요구**해서 한 칸
차이를 실패로 불렀습니다. 기준은 픽셀이 아니라 한 칸이어야 합니다.

**BGR과 RGB 평균.** `rtmlib` 은 cv2가 읽은 **BGR** 을 그대로 넣고 정규화 평균은 ImageNet의
**RGB 순서**를 씁니다 — 채널 0이 파랑인데 123.675(빨강 평균)를 받습니다. 모델은 RGB로
학습됐을 테니 어긋난 것이지만, **기준 결과를 만든 것이 그것**이므로 재현하려면 그대로
해야 합니다. 브라우저 구현이 "제대로" RGB를 넣으면 기준과 다른 값이 나옵니다.

### 경계 처리 — 예상대로 틀렸고 고쳤습니다

박스가 화면을 벗어나는 프레임이 clip 06에서 **355장 중 16장**, 최대 33.6px 넘칩니다.
드문 경로가 아닙니다.

`cv2.warpAffine` 은 기본이 `BORDER_CONSTANT` 값 0이라 화면 밖은 **검정**으로 채웁니다.
좌표를 클램프하면 가장자리를 복제하게 되는데, 그게 더 그럴듯해 보이지만 기준을 만든 것이
아닙니다. 가장 많이 벗어나는 프레임에서 평균 0.18 · 최대 4.31 어긋났습니다.

정규화하면 0은 `(0 − 123.675) / 58.395 = −2.118` 이고, **모든 참조 텐서의 최솟값이 정확히
−2.118** 입니다. 그게 단서였습니다. 검정으로 바꾸니 평균 0.0024 · 최대 0.0089 — 편한
프레임과 같은 반올림 수준이 되고, 전체 사슬도 발 키포인트 여섯 개 전부 0.000px,
24/26 정확히 일치(최대 차이는 역시 SimCC 한 칸)입니다.

## 그런데 박스 출처는 픽셀에서 무관하지 않습니다

검출기를 빼는 근거는 "MediaPipe가 이미 사람을 찾는다"였고, 그게 내려받기 예산을 떠받치는
유일한 가정이라 재봤습니다. 같은 프레임에 두 박스로 RTMPose를 돌려 비교했습니다.

```
박스 자체: 변마다 평균 89.3px 차이
  부호 있는 차이 (MediaPipe − 검출기)
    좌  +48.7px   상  +121.1px   우  −38.6px   하  −148.3px

키포인트 차이
  발    중앙 4.81px · 90% 11.18px · 최대 32.38px
  무릎   중앙 2.49px
  엉덩이  중앙 5.90px
```

SimCC 한 칸이 1.3px이니 발 키포인트 4.81px은 모델 해상도의 3.7배입니다. 110px짜리 발에서
양 끝이 그만큼 흔들리면 주법 각도로 약 5°이고, ±8° 경계에서는 무시할 수 없습니다.

차이는 **체계적**입니다 — MediaPipe 박스가 위로 121px 안쪽입니다. 랜드마크에 머리 정점이
없어서입니다. 하지만 표준편차가 10~34px이라 보정하면 계산이 아니라 **캘리브레이션**이
됩니다.

## 그래서 픽셀이 아니라 분석으로 판정했습니다

픽셀은 리포트가 만들어지는 재료가 아닙니다. 그래서 브라우저가 할 그대로 —
**MediaPipe 박스, 검출기 없음** — 창 전체를 돌려 TRC 어댑터(`halpe26ToPoseFrames`)와
`analyzeLandings` 를 통과시키고 Sports2D 실행과 비교했습니다.

```
clip 06 (트레드밀)
  Sports2D (검출기 박스)        착지 33 · 접지 313ms · 1.94BW · 168spm · 구간 17/17 · good
  RTMPose  (MediaPipe 박스)     착지 32 · 접지 330ms · 1.88BW · 166spm · 구간 17/17 · good
  MediaPipe 자세 (지금의 앱)     착지 31 · 접지 170ms · 2.87BW · 181spm · 구간 26/23 · fair

clip 04 (엘리트 주행)
  Sports2D (검출기 박스)        착지 33 · 접지 277ms · 1.99BW · 186spm · 구간 19/19
  RTMPose  (MediaPipe 박스)     착지 29 · 접지 292ms · 1.92BW · 183spm · 구간 18/18
  MediaPipe 자세 (지금의 앱)     착지 29 · 접지 306ms · 2.14BW · 145spm · 구간 21/14
```

**4.81px은 분석까지 전파되지 않습니다.** 브라우저 형태의 통과가 두 클립 모두에서
Sports2D를 따라갑니다 — 접지 +5%, 힘 −3%, 케이던스 1% 안, 그리고 **구간이 스트라이드마다
하나**. 지금의 앱은 clip 06에서 접지를 절반으로 재고 clip 04에서 케이던스를 22% 틀립니다.

clip 04에서 기준과 RTMPose가 둘 다 주법을 내지 않는 것도 일치입니다 — 제 경로가
기준이 판단을 보류하는 곳에서 같이 보류합니다.

**검출기는 필요 없습니다.** 근거는 키포인트 픽셀이 아니라 리포트가 쓰는 값들입니다.

### 남은 미검증

- **폰 성능** — 이제 유일하게 중요한 미측정 항목입니다.

## 여러 사람 — 실제로 일어나고, 재봤습니다

MediaPipe는 `numPoses: 1` 로 돌아 몸 하나를 돌려주지만 **어느 몸인지는 말하지 않습니다.**
검출기가 없으면 다른 사람을 잡았을 때 중재할 것이 없습니다.

Sports2D가 사람마다 파일을 따로 쓰기 때문에 답을 낼 수 있습니다 — 프레임마다 브라우저
박스가 **누구에게 가장 가까운지** 세면 됩니다. `subject-switch.ts` 가 그것입니다.

```
clip 04 (사람 13명)  기준 피사체에 가장 가까운 프레임 288/358 (80%)
   person02  288  ← 기준 (360프레임 전체 추적)
   person10   56
   person00   14
   다른 사람을 4프레임 이상 본 구간
     4–14   (11프레임) → person00
     295–311 (17프레임) → person10
     317–328 (12프레임) → person10
     334–347 (14프레임) → person10
     353–359  (7프레임) → person10

clip 06 (사람 1명)   355/355 (100%)
clip 05 (사람 1명)   322/360 (89%) — 부족분은 마지막 38프레임에서 Sports2D가
                     피사체를 놓친 것이고, MediaPipe가 바꾼 것이 아닙니다
```

**clip 04에서 프레임의 20%가 다른 사람입니다.** person10은 프레임 188에 들어와 끝까지
남는 두 번째 러너이고, 후반부에서 MediaPipe가 그쪽으로 옮겨 갑니다. 그 구간 발
키포인트는 기준과 중앙 233.6px 어긋납니다(정상 구간 9.3px).

그런데도 clip 04의 분석이 기준을 따라간 이유는 **그 20%가 중앙값을 움직이지 못했고**,
끼어든 사람이 마침 비슷하게 달리는 러너였기 때문입니다. 걷는 구경꾼이었으면 결과가
달랐을 것입니다. **운이 좋았던 것으로 기록합니다.**

### 박스 연속성 가드는 답이 아닙니다

제일 먼저 떠오르는 것이 "박스가 튀면 그 프레임을 버린다"입니다. 재봤습니다.

```
50px 넘는 오차 452개 중 도약 프레임이 41개 (9%)
도약 프레임: 50px 초과 55% · 200px 초과 51%
그 외 프레임: 50px 초과 20% · 200px 초과 12%
```

도약 프레임이 나쁜 것은 맞지만 **큰 오차의 9%밖에 설명하지 못합니다.** 91%는 박스가
정상적으로 움직인 프레임에서 나옵니다. 피사체가 서서히 옮겨 가면 도약이 없습니다.

프레임 크기 가설도 절반만 맞습니다 — 앞쪽 불일치 구간은 피사체가 화면의 25.2%로 작지만,
뒤쪽 불일치 구간은 32.9%로 깨끗한 구간(35.5%)과 비슷합니다.

### 답은 검출기가 아니라 `numPoses` 입니다

`src/lib/pose-engine.ts:31` 이 `numPoses: 1` 입니다. MediaPipe는 여러 명을 돌려줄 수
있으므로, 여러 개를 받아 **앞 프레임과 이어지는 쪽을 고르면** 검출기 없이 자체 추적이
생깁니다. 지금은 프레임마다 독립적으로 한 명을 받고 있어서 이어짐을 볼 기회 자체가
없습니다.

이건 이 문서가 제안하는 변경(자세 모델 교체)과 **별개이고 더 작습니다.** 그래서
**먼저 넣었습니다.**

### 넣고 다시 쟀습니다

`numPoses` 를 3으로 올리고, 프레임마다 **앞 프레임 피사체에 가장 가까운 몸**을 고릅니다
(`pickSubject`). 첫 프레임은 이어질 것이 없으므로 가장 큰 몸을 고릅니다 — 품질 게이트가
피사체에게 화면 높이의 4분의 1을 요구하는 것과 같은 생각입니다.

```
clip 04 기준 피사체에 가장 가까운 프레임
  이전  288/358 (80%) · 박스 도약 13
  이후  346/360 (96%) · 박스 도약  0
```

person10으로 새던 네 구간이 **전부 사라졌습니다.** 남은 것은 시작부 11프레임(4–14)이고,
그건 이어질 앞 프레임이 없어 키로 고르는 자리인데 하필 그 구간에서 의도한 러너가 화면의
25%로 가장 작습니다. 360분의 11입니다.

여섯 클립 전부 전후를 비교했습니다.

```
clip  이전                          이후                          기준
01   176spm · fair                176spm · fair                223spm
02   155spm · poor                166spm · poor                170spm
03   착지 3 · poor                 착지 5 · poor                 착지 24
04   145spm · 306ms · fair        186spm · 보류 · poor          186spm · 277ms
05   198spm · fair                198spm · fair                205spm
06   181spm · fair                181spm · fair                168spm
```

**잘 되던 클립은 하나도 변하지 않았습니다**(01·05·06 완전히 동일 — 사람이 한 명이라
고를 것이 없습니다). 틀렸던 곳에서 케이던스가 고쳐졌습니다 — clip 04가 145 → **186** 으로
기준과 정확히 같아지고, clip 02가 155 → 166(기준 170)으로 가까워집니다.

### 비용: clip 04가 fair에서 poor로 갑니다

숨기지 않고 적습니다. clip 04는 이제 접지와 힘을 **보류**합니다. 케이던스 일관성이
57% → 39%로 떨어지고 놓친 착지 추정이 3 → 8로 늘기 때문입니다.

이유는 나쁘지 않습니다. 이전의 "fair"는 **두 러너의 접지가 섞여 더 규칙적으로 보였던
것**이고, 그 위에서 케이던스를 22% 틀리게 발표하고 있었습니다. 한 사람으로 고정하니 이
클립에서 앱의 접지 검출이 실제로 4개를 놓치고 불규칙하다는 것이 드러납니다. **틀린 숫자를
내보내는 것보다 보류하는 편이 낫습니다.**

### 비용: 재 봤습니다 — 붐비는 클립에서만, 프레임당 5~13 ms

몸을 세 개 받으면 랜드마크 패스가 그만큼 돕니다. 처음에는 못 쟀습니다 — 같은 클립을
`numPoses` 3으로 173초, 1로 **255초** 로, 방향이 반대로 나왔습니다. `dump-browser.py` 의
시간에는 페이지 로드·모델 로드·고정 대기가 섞여 있었습니다.

그래서 **페이지 안에서 분석 루프만** 재게 하고, 탐색과 추론을 나눠 찍게 했습니다
(개발 전용, write-only — 리포트는 이 값을 읽지 않습니다).

#### 그래도 실행끼리 비교하면 안 됩니다

계측을 넣고 clip 04를 네 번 돌렸습니다. 순서를 **1-3-3-1** 로 둬서 꾸준한 드리프트가
상쇄되게 했습니다.

```
순서  설정    탐색    추론
 1   np=1   145ms   62ms
 2   np=3   109ms   42ms
 3   np=3   196ms   91ms
 4   np=1   189ms   89ms
```

상쇄해서 평균을 내면 추론이 np=1 75.5 ms, np=3 **66.5 ms** — 세 몸이 한 몸보다 9 ms
빠릅니다. 효과일 수 없는 방향입니다.

틀린 크기는 같은 표가 말해 줍니다. **탐색은 `numPoses` 에 의존할 수 없는데** 같은 방식으로
재면 np=3이 14.5 ms 빠르게 나옵니다. 그게 이 하네스의 잡음 바닥이고, 보려는 차이보다
큽니다. 페이지 로드를 걷어내도 **기계 자체가 실행 사이에 움직이는 것**은 남습니다.

#### 같은 프레임에서 비교하면 보입니다

두 설정을 한 페이지 안에 동시에 띄워 **같은 프레임**에 연달아 물었습니다
(`createProbeLandmarker`, `tools/sports2d/numposes-probe.py`). 그 순간의 기계 상태가
양쪽에 똑같이 적용됩니다. 어느 쪽을 먼저 부를지는 프레임마다 번갈아 바꿨습니다 — 두 번째
호출은 디코드된 이미지가 이미 따뜻한 상태를 만나기 때문입니다.

```
클립           몸(3 요청 시)  np=1 중앙  np=3 중앙  프레임 내 차이 중앙  3이 느린 프레임
04 (사람 13명)    1.28       96.7ms    101.9ms      +13.1ms          23/36
04 (사람 13명)    1.27       97.1ms    105.7ms       +5.7ms          35/56
04 (사람 13명)    1.27       98.0ms    106.9ms       +5.1ms          34/56
06 (사람 1명)     0.98       95.2ms     90.4ms       +2.9ms          32/56
06 (사람 1명)     0.98      100.2ms    103.1ms       -0.6ms          27/56
```

**붐비는 클립에서 프레임당 5~13 ms, 한 명짜리 클립에서는 0입니다.** 부호도 일관됩니다 —
clip 04는 세 번 다 양수이고 프레임의 62%에서 3이 느린 반면, clip 06은 부호가 뒤집히고
절반 근처(48~57%)로 동전 던지기입니다.

기계적으로 앞뒤가 맞습니다. `numPoses` 는 **상한이지 개수가 아닙니다.** 3을 요청해도
실제로 찾은 몸이 clip 04에서 평균 1.27개, clip 06에서 0.98개입니다. 추가 패스가 프레임당
0.3회 돌고 그게 5~13 ms이니 **몸 하나당 20~45 ms** 이며, 한 명뿐인 영상에서는 추가 패스가
아예 없어 비용도 없습니다.

#### 전체에서 차지하는 몫

프레임 하나가 210 ms 안팎이고 그중 추론이 123 ms 입니다(아래 절). **5~13 ms 는 프레임의
2~6%, 추론만 놓고 보면 4~11%** 입니다. 360프레임 기준 2~5초.

clip 04의 케이던스가 145 → 186 spm 으로 기준과 같아진 것이 그 대가로 얻은 것입니다.

## 폰에서 재 봤습니다 — 그리고 하네스가 거짓말을 하고 있었습니다

문서가 "유일하게 중요한 미측정 항목"으로 남겨 둔 것이 폰 성능입니다. 재려고 보니 먼저
고칠 것이 있었습니다.

### 하네스의 Chrome은 영상을 소프트웨어로 풉니다

`dump-browser.py` 가 붙는 Chrome은 `--headless=new --no-sandbox --disable-gpu` 로 떠
있습니다. 물어보면 바로 나옵니다.

```
포트 9223 (하네스)   powerEfficient false · ANGLE (Microsoft Basic Render Driver)
포트 9224 (GPU 켬)   powerEfficient true  · ANGLE (Intel Graphics)
```

`navigator.mediaCapabilities.decodingInfo` 의 `powerEfficient` 가 하드웨어 디코더를
쓰는지 답합니다. 하네스는 **안 씁니다.** 사용자의 브라우저는 씁니다.

이게 중요한 이유는 계측을 넣고 처음 나온 숫자가 "탐색이 패스의 70%" 였기 때문입니다.
같은 클립을 GPU를 켠 Chrome에서 돌리면 그 결론이 사라집니다.

```
clip 06 · 360프레임 · 12초 창

                            탐색     추론    프레임    360프레임
소프트웨어 디코드 (하네스)
  CPU 1x                 190·224  96·109   ~310ms   103·120초
  CPU 2x                     302     188    490ms      176초
  CPU 4x                 642·659 383·406  ~1025ms   369·383초
하드웨어 디코드 (GPU 켬)
  CPU 1x                   89·88 123·118    209ms    76·74초
  CPU 2x                     185     164    349ms      126초
  CPU 4x                     385     261    646ms      232초
```

**탐색이 207 ms 에서 89 ms 로 떨어지고, 더 비싼 쪽이 추론(123 ms)으로 바뀝니다.**
"탐색이 지배한다"는 것은 측정한 사실이 아니라 `--disable-gpu` 의 그림자였습니다.

그래서 실제 데스크톱 한 판은 **12초 클립에 75초** 입니다. 하네스가 말하던 103~120초가
아닙니다.

### 폰: 12초 클립에 약 4분

하드웨어 디코드를 켠 채 CPU만 늦추면 폰의 형태에 가까워집니다 — 폰도 디코드는 전용
하드웨어가 하고 추론은 CPU가 합니다. 4배는 웹 성능 작업에서 중급 폰의 관습적인 배수입니다.

```
CPU 1x   209ms/프레임    76초
CPU 2x   349ms/프레임   126초
CPU 4x   646ms/프레임   232초   ← 12초 클립에 3분 52초
```

**기본 경로로 쓸 수 없습니다.** 위에서 "중급 폰은 3~5배 느릴 수 있어 360프레임에
70~120초가 될 수 있다"고 추측했던 것은 낙관이었습니다. 그 추측은 RTMPose 부분만 센
것이고, 실제로는 **지금의 파이프라인만으로도** 4배 기기에서 232초입니다.

여기에 6단계 제안을 얹으면 이렇게 됩니다. RTMPose는 MediaPipe를 대체하지 않고 더해집니다
(MediaPipe가 박스를 줍니다).

```
             데스크톱                          4배 기기
지금     89 + 123        = 212ms →  76초    385 + 261        = 646ms → 232초
+RTMPose 89 + 123 + 141  = 353ms → 127초    385 + 261 + 564  = 1210ms → 436초
```

데스크톱에서 **+66%**, 4배 기기에서 **7분 16초** 입니다. 옵트인 "정밀 분석"이라는 자리
말고는 놓을 데가 없다는 뜻이고, 이건 위에서 제안한 방향과 어긋나지 않습니다 — 다만 이제
추측이 아니라 숫자입니다.

### 이 숫자들의 한계

**스로틀은 폰이 아닙니다.** 코어를 늦출 뿐 메모리 대역폭도, 다른 WASM SIMD 구현도,
4분짜리 실행에서 실제로 일어날 발열 스로틀링도 모사하지 않습니다. 셋 다 실제 폰을
**더 느리게** 만들 쪽이므로 232초는 낙관값으로 읽는 편이 안전합니다.

**RTMPose의 폰 숫자는 측정이 아니라 외삽입니다.** 141 ms 는 이 기계의 Node에서 잰
값이고, 거기에 스로틀 배수를 곱했습니다.

**탐색도 스로틀을 탑니다** — 하드웨어 디코드를 켜도 89 → 185 → 385 ms 로 배수를 따라
갑니다. 디코드 자체는 GPU가 해도 `seeked` 완료 처리가 늦춰진 메인 스레드에서 돌기
때문입니다. 그래서 "디코드는 하드웨어니 영향 없다"는 식으로 빼서 계산하면 안 됩니다.

### 여기가 최적화할 자리입니다

4배 기기의 646 ms 중 385 ms 가 탐색입니다. 프레임마다 `currentTime` 을 찍고 `seeked` 를
기다리는 대신 **순차 재생에서 프레임을 뽑으면** 디코더가 매번 되감지 않아도 됩니다.
`requestVideoFrameCallback` 이 그것을 위한 API입니다. 이 문서는 그걸 재 보지 않았고,
지금으로서는 자세 모델을 바꾸는 것보다 이쪽이 더 큰 수라고 봅니다.
