### 2. 판정 근거 계층

화면의 판정을 가르는 숫자들이 코드 곳곳에 상수로 흩어져 있었습니다. 각각 주석으로
설명돼 있었지만 **주석은 사용자에게 보여줄 수 없고**, 보고된 측정 범위를 반영한 값과
이 프로젝트가 그냥 정한 값이 구분되지 않았습니다.

`shared/thresholds.yaml` 이 유일한 원본이 되었습니다. 값마다 표시 이름, 근거,
검증 상태(`literature` / `derived` / `convention` / `internal` / `withheld`)를 답니다.
현재 26개 항목.

- `emit-thresholds.ts` 가 TS 모듈을 생성하고, 자체 검사가 메모리에서 다시 생성해
  디스크 파일과 비교합니다 — 어긋나면 테스트 실패
- YAML을 고른 이유: 다른 언어 구현이 그대로 읽어야 합니다. TS 상수로 두면 저쪽에서
  숫자를 손으로 옮기게 되고 그 순간 두 판정이 갈라집니다. pyyaml 로 파싱되는 것과
  26개 항목 전부 필드가 갖춰진 것을 실제로 확인했습니다
- 파서는 의존성 없이 30줄. 스키마가 2단 깊이 스칼라뿐이고, 들여쓰기 오타가 임계값
  하나를 다른 항목의 필드로 접어 넣으면 판정이 조용히 바뀝니다 — 그건 빌드를 멈춰야

`Footstrike.ts` 의 `±8°`, `40°` 는 숫자로 남겼습니다. `/downloads` 에서 단독 컴파일되는
규칙 파일이라 import 를 넣으면 다운로드본이 깨집니다. 대신 테스트가 리터럴과 YAML의
일치를 확인합니다 — 이 검사는 import 가 못 잡는 경우까지 잡습니다: **두 언어가 서로

### 3. 오버스트라이딩

접지 순간 발목이 엉덩이보다 얼마나 앞인지를 cm와 신장 대비 %로 잽니다. 두 결정이
값을 만듭니다.

**진행 방향을 발에서 읽습니다.** "앞"에는 방향이 필요한데, 몸이 화면을 가로지르는
방향은 이 분석이 원래 안 믿는 신호입니다(패닝 카메라가 몸 전체를 옆으로 밉니다). 발은
가는 쪽을 가리키므로 `발가락 − 뒤꿈치` 의 부호가 방향입니다. 테스트가 러너 전체를
좌우 반전시켜 값이 안 변하는지 확인합니다.

**값은 짧은 창의 전후방 최대값입니다.** 접지 구간이 뒤꿈치 롤인만큼 앞으로 늘려져
있어 그 지점을 그대로 읽으면 픽스처에서 약 1/4 낮게 나왔습니다. 최댓값은 우회로가
아니라 정의입니다 — 발이 앞으로 나아가다 멈추는 지점이 곧 착지 순간입니다.

판정은 보류합니다(`withheld`). 러닝에 합의된 경계가 없어 거리만 표시합니다.

### 4. 정면 촬영 지원 · 과내전/외전

정면 클립을 거부하는 대신 **두 번째 모드**로 읽습니다. 접지·체공·반력·케이던스는
정면에서도 유효하고, 관상면은 옆모습이 절대 보여줄 수 없습니다.

새 지표는 **디딘 다리의 무릎 안쪽 무너짐**과 **반대쪽 골반 내려감**이며, 접지 순간이
아니라 **지지 구간의 최대값**입니다 — 무릎이 가장 안으로 들어가는 것은 하중이 실린
중간 지지 구간이라, 접지 프레임을 재면 누구나 실제보다 잘 정렬된 것으로 나옵니다.

"안쪽"의 기준은 골반 축에서만 가져옵니다. 발 위치에서 가져오면 크로스오버 착지에서
부호가 뒤집히고, 진행 방향에서 가져오면 앞뒤를 구분해야 하는데 카메라 한 대로는
불가능합니다. 테스트가 같은 픽스처를 **후면에서 찍은 것처럼 좌우 반전**시켜 값이 한
자리도 안 변하는지 확인합니다.

**같이 고친 기존 버그.** 정면에서는 무릎이 카메라 축 방향으로 굽어 이미지 평면의
각도가 무의미한데, 그 값이 충격 점수 100점 중 18점을 차지하고 있었습니다. 무릎 굽힘을
시리즈 단계에서 비우고(재생 중 표시 경로도 함께), 점수는 무릎 항목을 빼고 남은 둘을
100점으로 다시 폅니다. 재정규화가 없으면 82점에서 잘려 최상위 구간이 도달 불가가
됩니다.

### 5. HUD 내보내기 · 얼굴 가리기

착지 한 장을 PNG로 저장합니다. 이미지에 들어가는 숫자는 화면과 같은 규칙을 따릅니다 —
정면 프레임에 주법이, 품질 부족 클립에 반력이 찍히는 일이 없습니다. **저장된 파일은
옆에 있던 단서보다 오래 남기 때문입니다.**

얼굴은 다른 것을 그리기 전에 가립니다. 영상이 기기 밖으로 안 나간다는 점은 그대로이고,
이미지가 앱이 만드는 것 중 **밖으로 나갈 수 있는 첫 파일**이라서 넣은 것입니다 —
프라이버시 보장이 아니라 공유용 장치입니다.

fail-closed 순서: 해당 프레임 랜드마크 → 앞뒤 프레임 → 화면 위 1/3 전체 → 그마저 안
되면 내보내지 않음. **순서가 핵심입니다.** "랜드마크가 없으니 가릴 것도 없다"가 바로
얼굴이 있는데 추적을 놓친 경우입니다.

이후 세 번 더 다듬었습니다.

- **어느 단계가 답했는지 이미지에 기록.** "적용이 안 된다"는 보고를 받았는데, 사진이
  없어 건너뛴 경우와 진짜 실패가 파일에서 똑같이 보였습니다. 얼굴에 관한 약속을
  "믿어 달라"로 두는 건 잘못된 모양입니다
- **미리보기에도 적용.** 오버레이는 아래 영상을 수정할 수 없으므로 가린 사본을 위에
  덮습니다. 카메라 프레이밍 중에는 랜드마크가 없어 초당 네 번 얼굴만 따로 추적합니다 —
  안 그러면 상단 1/3이 통째로 가려져 프레임을 잡을 수 없습니다
- **얼굴만 따라가도록.** 분석 전에는 추적이 없어 상단 슬래브로 떨어졌고, 박스가 머리
  폭의 약 3배였습니다. 줄이고 나니 옆모습에서 먼 쪽 눈·귀가 사라져 랜드마크 폭이
  절반이 되는 문제가 드러나, 코–어깨 거리로 머리 크기를 따로 재서 하한으로 씁니다

### 6. 모자이크 → 블러

반경을 **얼굴 폭의 1/6**로 잡았습니다. 원래 모자이크를 고른 이유가 "고정 픽셀 블러는
해상도가 커지면 아무것도 못 가린다"였는데, 반경을 얼굴에 비례시키면 그 문제가 없어집니다.

모자이크는 **안전망으로 남겼습니다.** 캔버스가 `filter` 를 무시하는 브라우저라면
블러가 원본을 그대로 다시 그리고 성공했다고 보고합니다 — 얼굴이 드러난 채 아무 신호도
없는, 이 모듈이 막으려는 바로 그 실패입니다.

처음 넓히고 보니 사각형 경계가 그대로 보여 붙여 놓은 판때기처럼 읽혔습니다. **타원으로
자르고 가장자리를 알파 그라디언트로 풀었습니다** — 클립은 자르는 것밖에 못 하므로 별도
레이어에 그려 알파를 깎습니다. 완전히 덮는 부분은 안쪽 2/3이고, 풀리는 건 머리 둘레의
여백뿐입니다.

### 8. 카탈로그 드리프트 · 동점 정렬

파이썬 트랙의 통합 보고서를 대조했습니다. 보고서의 검증 수치가 제 카탈로그와 정확히
일치했습니다(105행, 리어풋 67 / 미드풋 63 / 포어풋 42, 다중 라벨 17종). 다만 같은
결함의 **다른 형태가 이 저장소에도** 있었습니다.

**`shoes.json` 이 `shoes.csv` 와 조용히 어긋날 수 있었습니다.** 앱이 읽는 것은 JSON
이고 사람이 고치는 것은 CSV인데, 둘을 맞추는 장치가 주석 한 줄뿐이었습니다. 파서를
공용 모듈로 옮겨 생성기와 테스트가 같은 코드를 쓰게 했습니다.

**동점이 CSV 행 순서로 갈렸습니다.** 행을 뒤집어 실제로 돌려 보니 6개 조합 중 4개에서
추천이 바뀌었습니다. CSV가 저장소 안에만 있을 때는 행 순서가 통제 아래였지만, 공유
파일이 되는 순간 통제를 잃습니다. 새 순서는 점수 → 주법 라벨이 더 좁은 쪽 → 사진이
있는 쪽 → 브랜드명 → 모델명입니다. **추천 결과는 이전과 동일**하고, 바뀐 것은 공유
CSV를 다시 정렬해도 흔들리지 않는다는 점입니다.

않아도 같은 모양**입니다.

- **업로드 상자**: 내용과 무관하게 16:9를 유지해서 비어 있을 때(모두가 처음 보는 화면)
  옆 카드보다 짧아 카드 아래 1/3이 비어 있었습니다. 이제 행 높이만큼 자라고, 받는
  형식과 읽는 길이도 적습니다
- **3분할 띠**: 모바일에서 구분선만 있는 빈 표처럼 보였습니다. 스펙 목록으로 바꿨습니다
- **착지 카드 9개**: 전부 펼쳐진 벽이었습니다. 한 줄 행으로 접고 고른 것만 펼칩니다.
  접힌 줄에 반력·부하율·무릎이 남는 것은 취향이 아닙니다 — `Rule §UI` 가 점수가 보이는
  곳에는 점수를 움직이는 값도 보이라고 정해 두었습니다
- 클립 카드가 `01` 을 갖게 되어 번호가 `02` 부터 시작하지 않습니다

### 11. 요약 평서문화

가장 많이 읽히는 문장이 `평균 2.1 BW` 로 시작하고, 페이스 칸이 `듀티 0.38` 로 자기를
설명했습니다. README를 읽지 않은 사람에게는 정확하지만 아무 뜻이 없습니다.

| 전 | 후 |
|---|---|
| `평균 2.1 BW` | `착지 충격은 체중의 2.1배` |
| `듀티 0.38` | `한 걸음의 38%를 땅에서` |
| `부하율 21 BW/s` | `0–100. 낮을수록 충격을 나눠 받은 착지` |

항상 보이는 숫자를 7개에서 4개로 줄였습니다(페이스·주법·충격·횟수). 나머지는 후속
질문에 답하는 것들이라 세부로 옮겼습니다. 요약 카드 1,360 → 962px.

### 12. 케이던스 재조정

**지적이 맞았고, 편향은 의도적이었습니다.** 착지 간격의 40번째 백분위수를 쓰고
있었는데, 착지를 놓쳐 간격이 두 배가 된 경우를 지나치려고 짧은 쪽으로 기울인
것입니다. 방향이 반대였습니다.

| 참값 | 이전 | 지금 |
|---:|---:|---:|
| 136 | 138 | 136 |
| 176 | 180 | 176 |
| 250 | 257 | 250 |

게다가 접지가 한 번이라도 쪼개지면 두 배로 나왔습니다. 중앙값으로 바꾸고, 절반 간격은
두 가지로 막았습니다. 일부만 쪼개진 경우는 더 많이 반복되는 간격을 쓰고, 대부분
쪼개진 경우는 **발은 자기가 속한 걸음보다 오래 땅에 붙어 있을 수 없다**는 물리적
제약으로 판정합니다. 진짜 빠른 케이던스(250)와 걷기(접지가 걸음보다 긴 경우)를 잘못
반토막 내지 않는지도 테스트합니다.

### 13. 세션 비교 판정

체공 시간이 `약 150 ms → 약 120 ms` 인데 아래에 `변화 없음` 이 찍혔습니다. 결함이
두 개였고 카드가 둘을 한꺼번에 보여주고 있었습니다.

**하나 —** 오차 기준이 한 번의 측정 기준으로 적혀 있는데 비교 대상은 한 클립의 모든
착지 평균입니다. 9회 평균은 1회보다 약 3배 안정적이라, 단일 측정 기준으로 재면 진짜
차이가 버려집니다. 이제 착지 수에 따라 기준이 좁아집니다(9회 상한 — 그 이상은 표본이
독립이 아니라 평균의 표준오차 모델이 맞지 않습니다).

**둘 —** 표시값은 반올림되므로(시간 30ms, 반력 0.1) 앱이 구분하지 못하는 두 값이 서로
다른 칸에 떨어지면 카드가 스스로 모순됩니다. 변화가 없으면 **숫자를 하나만** 보여줍니다.
숫자가 둘이면 변화를 찾은 것이고, 하나면 못 찾은 것입니다.

## 제가 만든 버그

기록의 신뢰를 위해 함께 적습니다.

**`--spacing-block` 토큰이 `inline-block` 을 망가뜨림.** Tailwind는 모든
`--spacing-<이름>` 을 `inline-<이름>`(inline-size) 유틸리티로도 만듭니다. 토큰을
`block` 이라 지어서 `inline-block` 이 두 뜻을 갖고 **둘 다 출력**됐습니다. 앱의 모든
`inline-block` 요소가 3.5rem 폭으로 고정되고, 헤더 버튼이 56px에 한 글자씩 4줄로
헤더 위로 넘쳤습니다. 빌드·타입·린트 전부 침묵했고 클래스 이름은 그대로 읽혔습니다.
브라우저에 "이 폭을 정한 규칙이 뭐냐"고 물어서야 답이 나왔습니다. → 토큰 이름을 바꾸고,
display 키워드와 겹치는 이름을 테스트가 거부하게 했습니다.

**사진 그리기와 얼굴 가리기를 같은 조건에 묶음.** 가리기를 끄고 저장하면 영상 프레임이
통째로 빠져 검은 배경에 관절선만 나왔습니다. 켬 상태만 확인했으면 못 봤을 버그입니다
(파일 크기 891KB → 65KB로 잡았습니다). → 두 결정을 분리하고 테스트로 고정했습니다.

**붉은·노란 색감.** 위 1번. 요청대로 만들었지만 결과가 틀렸고, 왜 틀렸는지를
기록했습니다.

npm run test:analysis   # 픽스처·경계값·근거 계층·카탈로그·내보내기 (32개 항목)

가로 넘침(`scrollWidth == 390`)을 함께 봤습니다. 얼굴 가리기는 실제 러닝 영상으로
분석부터 저장까지 돌렸습니다.
