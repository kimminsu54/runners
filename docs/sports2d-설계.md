# Sports2D 도입 설계 — 착지 주법 분석의 정확도와 신뢰도

작성 2026-09-02 · 기준 커밋 `70aeced` · 상태 **설계 (배포 경로 미결정)**

목적은 두 가지이고 서로 다릅니다.

- **정확도**: 같은 영상에서 더 참값에 가까운 각도·시점을 얻는 것
- **신뢰도**: 우리가 내는 값의 오차를 **숫자로 말할 수 있는 것**

지금 앱은 두 번째를 전혀 못 합니다. `shared/thresholds.yaml` 의 26개 항목 중
`literature` 4개, `derived` 4개이고 나머지는 `internal` / `convention` / `withheld`
입니다. 즉 화면의 숫자가 얼마나 틀렸는지 아무도 모릅니다. Sports2D를 도입하는 진짜
이유는 **기준 도구를 갖는 것**입니다.

---

## 1. 지금 정확도를 깎는 것들

코드에서 확인한 것만 적습니다.

| # | 원인 | 위치 | 영향 |
|---|---|---|---|
| 1 | MediaPipe Pose **lite**, IMAGE 모드, CPU/WASM | `pose-engine.ts` | 세 변형 중 가장 낮은 정확도 |
| 2 | 주법을 `heel`→`foot_index` **두 점**의 이미지 평면 각도로 판정 | `footStrikeAngleDeg` | 발 랜드마크는 MediaPipe에서 가장 불안정한 부위 |
| 3 | 원본 영상이 보통 30fps | — | 접지 타이밍 해상도 ±33ms. 스프린트 스탠스 100ms의 1/3 |
| 4 | 스케일이 **신장 가정**에서 나옴 (`코–발꿈치 px / 0.92`) | `measureSubject` | 개인차·자세·원근이 모두 이 한 상수로 흡수됨 |
| 5 | 궤적 필터가 **이동평균뿐** (창 3~5) | `analyzeLandings` | 저역통과가 아니라 창 평균 — 접지 에지가 둔해짐 |
| 6 | 바닥 기준선을 planted 프레임의 중앙값으로 **추정** | `normalizeFootAngles` | 카메라 롤·경사가 주법 각도에 그대로 섞임 |
| 7 | 반력이 듀티 팩터에서 **모델링**된 값 | `peakForceFromDuty` | 측정이 아님. Sports2D도 이건 못 고침 |

4번과 6번이 특히 큽니다. **주법 판정은 각도 8도를 다투는데, 그 각도의 기준선 자체를
추정하고 있습니다.**

## 2. Sports2D가 실제로 바꾸는 것

[Sports2D](https://github.com/davidpagnon/Sports2D) (BSD 3-Clause, JOSS 게재)는
RTMLib/RTMPose 기반 파이썬 도구입니다.

### 2-1. 발 전용 키포인트 6개

기본 모델 `body_with_feet` 는 [HALPE_26](https://github.com/Fang-Haoshu/Halpe-FullBody)
을 씁니다.

| | MediaPipe Pose (33) | HALPE_26 |
|---|---|---|
| 발꿈치 | `29` / `30` | `24` / `25` |
| 엄지발가락 | — | `20` / `21` |
| 새끼발가락 | — | `22` / `23` |
| 발끝 | `foot_index 31` / `32` (단일) | — |

MediaPipe의 `foot_index` 는 발끝 한 점입니다. HALPE_26은 **엄지와 새끼를 따로** 줍니다.
그래서 발의 장축을 `발꿈치 → (엄지+새끼)/2` 로 잡을 수 있습니다 — 발이 밖으로 돌아간
(toe-out) 자세에서 한 점 방식보다 훨씬 안정적입니다. 위 1절 2번 원인에 직접 대응합니다.

### 2-2. 제대로 된 필터 체인

Sports2D 기본 파이프라인: 결측 보간(10프레임 이하) → **Hampel 이상치 제거** →
**Butterworth 6Hz 4차**. 설정으로 Kalman, One Euro, GCV spline, LOESS 등 교체 가능.

우리 이동평균(1절 5번)을 대체합니다.

### 2-3. 미터 스케일과 바닥 각도

신장(`--first_person_height`)으로 픽셀→미터를 계산하고, **바닥 각도를 운동학에서 자동
검출**하며, 원근 보정(카메라 거리 / 초점거리 / 화각)을 받습니다. 캘리브레이션 `.toml`
도 지원.

1절 4번과 6번에 직접 대응합니다.

### 2-4. 사람 추적

여러 사람을 동시에 추적하고 몇 프레임 사라져도 ID를 유지합니다. 선택 기준을 지정할 수
있습니다(`highest_likelihood`, `largest_size`, `greatest_displacement` 등). 지나가는
사람이 포즈를 가로채는 문제가 없어집니다.

### 2-5. 출력

`.trc`(픽셀·미터), `.mot`(관절·분절 각도, OpenSim), `.c3d`, 주석 영상, 그래프.
`--do_ik` 로 OpenSim 역기구학까지 갑니다.

## 3. Sports2D가 바꾸지 않는 것

과대평가를 막기 위해 원문 그대로 적습니다.

> "Angle estimation is only as good as the pose estimation algorithm, i.e., it is not
> perfect."
> "Results are acceptable only if the persons move in the 2D plane (sagittal or
> frontal). The persons need to be filmed as parallel as possible to the motion plane."
> "The Z coordinate (depth) should not be overly trusted."
> "Right/Left swaps are not corrected yet."

정리하면:

- **여전히 카메라 한 대의 2D 투영**입니다. 촬영면과 어긋난 각도는 그대로 오차로 남습니다
- **프레임률이 접지 타이밍을 여전히 제한**합니다. 30fps 영상은 30fps 해상도입니다
- **반력은 여전히 미측정**입니다. 듀티 팩터 모델이 그대로 쓰입니다
- **주법 경계 ±8°의 러닝 검증 부재는 그대로**입니다. 더 정확한 각도를 재도, 그 각도를
  가르는 경계에 근거가 생기는 것은 아닙니다 → `convention` 상태 유지
- 좌우 스왑이 보정되지 않아 좌우 비대칭 지표는 별도 검증이 필요합니다
- 결측 보간(10프레임 이하)이 **측정값과 구분되지 않고** 출력에 섞입니다. 보간된 프레임을
  관측으로 취급하면 품질 게이팅이 무력해집니다

## 4. 아키텍처 충돌 — 결정해야 할 것

Sports2D는 Python 3.11+ / onnxruntime입니다. **브라우저에서 돌아가지 않습니다.**

이 앱의 첫 번째 약속은 히어로에 적혀 있습니다: *영상은 업로드되지 않고 브라우저 안에서만
처리됩니다.* 세 가지 길이 있고, 각각 무엇을 얻고 무엇을 잃습니다.

| | 무엇을 얻나 | 무엇을 잃나 | 서버 |
|---|---|---|---|
| **A. 오프라인 기준 도구** | 우리 값의 오차를 숫자로 알게 됨. 임계값 근거 승급 | 제품 정확도는 그대로 | 없음 |
| **B. 정밀 분석 경로** | 사용자가 원할 때 정확한 분석 | 그 순간 영상이 서버로 감 (선택적) | 필요 |
| **C. 전면 교체** | 항상 정확 | **약속을 잃음.** 무료 트랙의 존재 이유가 사라짐 | 필수 |

**A → B 순서를 권합니다.** A 없이 B를 만들면 "정밀"하다는 주장을 증명할 방법이 없습니다.
그리고 A는 서버도, 약속 변경도, 사용자 동의도 필요 없습니다. 비교 문서의 포트폴리오
설계(무료=브라우저 / 유료=서버, "정밀 분석" 선택 버튼)와도 정확히 맞습니다.

C는 권하지 않습니다. 이 앱이 다른 도구와 구별되는 지점이 그 약속입니다.

## 5. 핵심 설계 — 어댑터 한 장

`analyzeLandings(frames: PoseFrame[], options)` 는 **순수 함수**입니다.

```ts
type PoseFrame = { t: number; landmarks: Landmark[] | null };
type Landmark  = { x: number; y: number; z?: number; visibility?: number };
```

`x`, `y` 는 0~1 정규화 좌표이고, 인덱스는 MediaPipe 33개 규격입니다. 즉 **포즈 추정기만
갈아끼우면 분석 로직 전체를 그대로 재사용**할 수 있습니다.

```
Sports2D → *_px.trc ──[어댑터]──▶ PoseFrame[] ──▶ analyzeLandings ──▶ 같은 리포트
MediaPipe ────────────────────────▶ PoseFrame[] ──▶ analyzeLandings ──▶ 같은 리포트
```

이게 설계의 중심입니다. 어댑터가 있으면:

- **오프라인 비교**가 통제 실험이 됩니다 — 같은 클립, 같은 분석기, 포즈 추정만 다름.
  차이는 전부 포즈 추정에서 온 것입니다
- **나중에 B로 갈 때** 서버는 `.trc` 만 돌려주면 되고, 클라이언트 분석기가 그대로 씁니다.
  분석 로직을 파이썬으로 옮겨 적을 필요가 없습니다 — 그게 두 벌로 갈라지는 시작입니다

### 5-1. 키포인트 매핑

`analyzeLandings` 가 실제로 읽는 것만 채우면 됩니다.

| MediaPipe 인덱스 | HALPE_26 | 쓰는 곳 |
|---|---|---|
| `0` nose | `0` Nose | 신장 측정, 얼굴 박스 |
| `2` / `5` eye | `1` / `2` LEye/REye | 얼굴 박스 |
| `7` / `8` ear | `3` / `4` LEar/REar | 얼굴 박스 |
| `11` / `12` shoulder | `5` / `6` | 옆모습 판정, 머리 크기 |
| `23` / `24` hip | `11` / `12` | 무게중심, 골반 기울기 |
| `25` / `26` knee | `13` / `14` | 무릎 각도, 정면 정렬 |
| `27` / `28` ankle | `15` / `16` | 접지 검출, 몸 앞 착지 |
| `29` / `30` heel | `24` / `25` LHeel/RHeel | 접지 검출, 주법 각도 |
| `31` / `32` foot_index | `20` / `21` LBigToe/RBigToe | 주법 각도 |

`9` / `10` mouth 는 HALPE_26에 없습니다 → `visibility: 0` 으로 채웁니다. 얼굴 박스는
코·눈·귀 5점으로 충분히 잡힙니다(현재 코드도 2점 이상이면 동작).

**새끼발가락 `22`/`23` 은 MediaPipe에 대응이 없습니다.** 33개 배열에 그냥 담을 수 없으니,
발 장축을 개선하려면 `PoseFrame` 에 선택 필드를 추가해야 합니다:

```ts
type PoseFrame = {
  t: number;
  landmarks: Landmark[] | null;
  /** 발 전용 키포인트가 있는 추정기에서만 채워집니다. */
  footExtras?: { leftSmallToe?: Landmark; rightSmallToe?: Landmark };
};
```

`footStrikeAngleDeg` 가 이게 있으면 `발꿈치 → (엄지+새끼)/2`, 없으면 지금처럼
`발꿈치 → 엄지` 를 씁니다. 두 경로가 같은 함수 안에 있어야 비교가 가능합니다.

### 5-2. 이중 필터링 — 반드시 처리할 것

Sports2D 출력은 이미 Butterworth 6Hz를 통과했습니다. 여기에 우리 이동평균(창 3~5)을
또 걸면 **접지 에지가 둔해져 접지 시간이 늘어나고, 반력이 과소평가**됩니다. 지금 코드는
반대 방향의 보정(`stance_edge_allowance_s = 0.04`)까지 넣어 두었으므로 오차가 겹칩니다.

```ts
type AnalyzeOptions = {
  // ...
  /** 입력이 이미 저역통과를 통과했는지. 통과했으면 내부 평활을 줄입니다. */
  preFiltered?: boolean;
};
```

이 플래그가 없으면 비교 실험 자체가 무의미합니다 — Sports2D 쪽이 항상 접지가 길게
나올 것이고, 그걸 포즈 추정 차이로 잘못 읽게 됩니다.

### 5-3. 스케일과 바닥

Sports2D의 미터 `.trc` 를 쓰면 `measureSubject` 의 `staturePx = px / 0.92` 가정을
건너뛸 수 있습니다. 바닥 각도도 Sports2D가 검출하므로 `normalizeFootAngles` 의 추정
기준선 대신 쓸 수 있습니다.

다만 **한 번에 다 바꾸지 마세요.** 어느 변경이 어떤 차이를 만들었는지 구분할 수 없게
됩니다. 순서는 6절에 있습니다.

## 6. 검증 설계 — 신뢰도는 여기서 나옵니다

Sports2D도 2D 추정이므로 **정답이 아닙니다.** 기준을 3단으로 둡니다.

| 단 | 기준 | 무엇을 말해 주나 | 비용 |
|---|---|---|---|
| 1 | MediaPipe ↔ Sports2D **일치도** | 불일치가 크면 브라우저 값을 못 믿는다는 *증거* | 낮음 |
| 2 | 240fps 슬로우 클립의 **수동 라벨** | 접지 프레임과 주법의 실질적 기준 | 중간 |
| 3 | Sports2D `--do_ik` **OpenSim 역기구학** | 관절각의 상위 기준 | 높음 |

1단만으로는 정확도를 말할 수 없습니다. **둘이 다르다는 사실만** 알 수 있습니다. 실제
정확도 주장에는 2단이 필요합니다.

### 6-1. 표본

| 축 | 수준 |
|---|---|
| 페이스 | 편한 / 중간 / 빠른 (3) |
| 주법 | 리어풋 / 미드풋 / 포어풋 (3) |
| 촬영 각도 | 정확한 옆모습 / 15~30° 사선 (2) |

**최소 18클립 × 클립당 8착지 이상 = 144착지.** 사선 축을 넣는 이유는 Sports2D 자신이
"촬영면과 평행하게" 를 조건으로 걸기 때문입니다 — 그 조건이 깨질 때 얼마나 나빠지는지가
우리가 품질 게이팅에 써야 할 숫자입니다.

### 6-2. 지표

- **접지 프레임 차이**: 프레임 단위 분포 (중앙값, 90퍼센타일)
- **발 경사각 RMSE**: 프레임별, 그리고 접지 순간만
- **주법 분류 일치**: 혼동 행렬 + Cohen's κ. 정확도 %만으로는 3분류의 우연 일치를
  가릴 수 없습니다
- **접지·체공 시간**: Bland-Altman (편향과 일치 한계). 차이-평균 산점도라야 "얼마나
  다른가" 가 아니라 "어디서 다른가" 를 봅니다
- **케이던스**: 이미 픽스처로 ±1 spm까지 잡았으니, 실영상에서의 편향만 확인

### 6-3. 산출물

검증이 끝나면 **`shared/thresholds.yaml` 이 갱신됩니다.** 이게 이 작업의 최종 목적입니다.

- `foot_strike_rearfoot_max_deg` / `forefoot_min_deg`: `convention` → 라벨 세트와의
  일치도가 나오면 `literature` 또는 근거 문장이 붙은 `internal`
- `side_view_max_profile_ratio` (0.14): 사선 축 결과로 재보정. 지금은 순수 추측
- `min_subject_height_ratio` (0.2): 사람 크기별 오차 곡선에서 결정
- `stance_edge_allowance_s` (0.04): 수동 라벨된 접지 프레임과의 차이로 직접 측정
- **새 항목**: `foot_strike_angle_rmse_deg` 같은 *측정 오차* 를 넣고, 화면의 주법 표시에
  `약 0° (±3°)` 처럼 오차를 함께 내보냅니다

마지막 항목이 사용자에게 보이는 변화입니다. 지금은 `약 0°` 라고만 적습니다.

## 7. 단계 계획

| 단계 | 하는 일 | 산출물 | 선행 |
|---|---|---|---|
| 0 | Sports2D 실행 환경 + 샘플 클립 1개 처리 | `.trc` / `.mot` 확인 | — |
| 1 | `.trc` → `PoseFrame[]` 어댑터 + `preFiltered` 플래그 | `tools/` 스크립트, 단위 테스트 | 0 |
| 2 | 같은 클립 양쪽 파이프라인 비교 리포트 | 지표 CSV + 요약 | 1 |
| 3 | 라벨 세트 구축 (240fps, 18클립) | 라벨 CSV | — (병행 가능) |
| 4 | 정확도 산출 → 임계값 재보정 | `thresholds.yaml` 갱신 | 2, 3 |
| 5 | 발 장축 개선 (`footExtras`), 미터 스케일, 바닥 각도 — **하나씩** | 각각의 개선폭 | 4 |
| 6 | (결정 시) 정밀 분석 서버 경로 | API + 동의 UI | 4 |

3단계가 실제로 가장 오래 걸립니다. 240fps로 18클립을 찍고 착지마다 접지 프레임과 주법을
사람이 라벨하는 일이며, **이 작업 없이는 정확도를 숫자로 말할 수 없습니다.**

---

## 8. 결정이 필요한 것

1. **배포 경로**: A(오프라인 기준 도구)까지인가, B(정밀 분석 경로)까지 갈 것인가
2. **코드 위치**: Sports2D 래퍼를 이 저장소 `tools/` 에 둘 것인가, 파이썬 트랙
   저장소에 둘 것인가. 파이썬 트랙에 두면 그쪽 의존성과 섞이고, 이쪽에 두면
   파이썬 환경이 이 저장소에 생깁니다
3. **라벨링 주체와 일정**: 3단계는 사람 손이 필요합니다
4. **하드웨어**: onnxruntime CPU로 충분한지, GPU가 필요한지 — 18클립 오프라인
   처리라면 CPU로도 되지만 반복 실험이면 GPU가 시간을 줄입니다
